# Backend Architecture Documentation

This document describes the design, architectural boundaries, and implementation patterns of the Galvão backend.

---

## 1. Architectural Style: Clean Architecture & CQRS

The Galvão backend is designed using Clean Architecture principles combined with the Command Query Responsibility Segregation (CQRS) pattern. This enforces strict separation of concerns, ensures the core business logic (Domain) remains technology-agnostic, and allows the system to scale reads and writes independently.

### Layer Dependencies
The project is split into four distinct layers in `backend/src/`:
1. **Galvao.Domain**: Represents the enterprise/domain core. It has **zero dependencies** on external frameworks, databases, or other project layers.
2. **Galvao.Application**: Defines use cases, query/command contracts, validations, and infrastructure interfaces. It depends *only* on `Galvao.Domain` and `Galvao.Shared`.
3. **Galvao.Infrastructure**: Integrates the database provider (EF Core + MySQL), security providers (ASP.NET Core Identity), and third-party APIs (Resend CRM). It depends on `Galvao.Application`.
4. **Galvao.Presentation**: Exposes API endpoints (ASP.NET Core Controllers), sets up dependency injection, and configures middlewares. It depends on `Galvao.Infrastructure`.
5. **Galvao.Shared**: Contains shared utility models (e.g. `Result`, `Error` classes) used across all projects.

```text
[ Presentation ] ──> [ Infrastructure ]
       │                      │
       ▼                      ▼
  [ Application ] ───────> [ Domain ]
       │                      │
       ▼                      ▼
           [ Galvao.Shared ]
```

## 2. Domain Layer (`Galvao.Domain`)

The Domain layer defines the business entities, state invariants, and factory methods:
* **BaseEntity**: Abstract base class defining UUID Version 7 primary keys (`Id`), creation timestamps (`CreatedAt`), update timestamps (`UpdatedAt`), and logical deletion indicators (`Active`).
* **Member**: Holds the profile details (First/Last name, Display name, Opt-in flags). Contains a `PendingSync` boolean to indicate if local changes are out of sync with Resend CRM, and methods (`MarkAsPendingSync()`, `ClearPendingSync()`, `UpdateMarketingPreferences(...)`) to manage states.
* **ConsentLog**: Models marketing preference change transactions for GDPR/LGPD compliance. Tracks `MemberId`, `Action` ("Opt-In" / "Opt-Out"), client `IpAddress`, client request `Source` web route, and a unique cryptographic `ConsentToken`.
* **MemberContact**: Tracks the external Resend CRM contact synchronization. Includes the `ExternalContactId` generated by Resend.
* **EmailSegment**: Sub-model linked in a one-to-many relationship under `MemberContact`. Maps opt-in mailing segments (e.g. `news`, `promotions`) with subscription/unsubscription dates.
* **EmailAuditLog**: Models a delivery validation audit record for outgoing email communications. Tracks recipient, subject, email provider client used, message category, status code, external ID, error details, and timestamp.
* **RemovedUser**: GDPR compliance log tracking accounts that requested their data to be purged. Records status flags indicating successful erasure of personal details, auth credentials, marketing data, and Resend contacts.
* **ShowroomItem**: Represents an item displayed in the showroom catalog. Contains title, price, category, and encapsulated photo gallery properties.
* **ShowroomItemPhoto**: Models the photos associated with a showroom item, including URL and primary display status indicator.
* **Article**: Models news articles. Contains behavior transitions (`Publish()`, `Unpublish()`).

> [!NOTE]
> Database class mappings and relationship configurations are documented in the [Domain Class Diagram](../diagrams/class/class_diagram.md).

## 3. Application Layer (`Galvao.Application`)

The Application layer coordinates execution flows using CQRS handlers.

### CQRS Abstractions
The folder `Common/CQRS/` defines basic handler contracts:
* `ICommand`: Represents write actions.
* `ICommandHandler<TCommand>`: Executes commands returning a simple `Result` (success/failure status).
* `ICommandHandler<TCommand, TResponse>`: Executes commands returning a wrapper `Result<TResponse>`.
* `IQuery<TResponse>`: Represents read queries.
* `IQueryHandler<TQuery, TResponse>`: Executes queries returning a wrapper `Result<TResponse>`.

### Core Use Cases Mappings
* **Articles**:
  * `CreateArticleCommand` -> Creates drafts.
  * `UpdateArticleCommand` -> Modifies article details.
  * `PublishArticleCommand` -> Publishes or unpublishes articles.
  * `GetArticleByIdQuery` / `GetPagedArticlesQuery` -> Reads article data.
* **Showroom**:
  * `CreateShowroomItemCommand` / `UpdateShowroomItemCommand` -> CRUD operations for items.
  * `AddShowroomItemPhotoCommand` / `RemoveShowroomItemPhotoCommand` -> Updates associated images.
  * `GetShowroomItemByIdQuery` / `GetPagedShowroomItemsQuery` -> Reads catalog listings.
* **Members**:
  * `UpdateMemberProfileCommand` -> Updates names and display names.
  * `UpdateMarketingPreferencesCommand` -> Updates marketing preference flags, logs opt-in/opt-out auditing transactions via `ConsentLog`, and triggers Resend CRM updates.
    * **CancellationToken Propagation**: Every step of the handler (`GetByIdAsync`, `AddAsync`, `UpdateExistingContactAsync`, `SaveChangesAsync`) propagates the request's `CancellationToken` to terminate execution early if the client cancels the HTTP request, preventing zombie tasks and database connection leaks.
    * **Decoupled Downstream Sync Fallback**: If the external Resend CRM sync fails (due to API rate-limiting or network outage), the handler catches the exception, marks the local member profile as `PendingSync = true`, and logs a console alert. The transaction then proceeds to persist the local changes (profile settings + consent log) to MySQL, ensuring user action is not blocked by external API failures. If sync succeeds, any pending sync is cleared (`PendingSync = false`).
  * `ChangeEmailCommand` -> Replaces the user's primary login and profile email, invokes Resend CRM to delete the old email contact, and creates a fresh contact with the new email.
  * `ChangePasswordCommand` -> Updates the user's secure password hash inside the ASP.NET Identity database.
  * `PurgeUserCommand` -> Implements the GDPR deletion workflow. Validates the password, deletes the contact in Resend CRM, removes the local CRM tracker (`MemberContact`) and the local profile (`Member`), deletes the Identity `Account`, and records a `RemovedUser` compliance log.
* **Roles / Users**:
  * Assigns roles, blocks accounts, handles logins, registrations, and token refreshments. Allows administrators to query all roles or inspect specific role assignments.

## 4. Infrastructure Layer (`Galvao.Infrastructure`)

The Infrastructure layer implements data persistence, authentication, and external services.

### MySQL Persistence & Relationships
The system uses MySQL. Entity configurations in `Persistence/Configurations/` apply specific schema layouts:
* **Shared Primary Key One-to-One Pattern**:
  * `Account` (Identity credentials) is the parent entity.
  * `Member` shares the primary key (`Member.Id` references `Account.Id`) with cascade delete.
  * `MemberContact` shares the primary key (`MemberContact.Id` references `Member.Id`) with cascade delete.
  * *Rationale*: Guarantees perfect entity synchronization across auth, profiles, and CRM tracking, without requiring separate foreign key columns or complex lookups.
* **Showroom Item Photos**:
  * Mapped as a one-to-many relationship. The private field `_photos` backing field is configured in EF Core (`builder.Navigation(s => s.Photos).UsePropertyAccessMode(PropertyAccessMode.Field)`).
* **Consent Auditing Ledger**:
  * `ConsentLog` is persisted to the `ConsentLogs` table via the `ConsentLogConfiguration` mapping.
  * Mapped as a one-to-many relationship (`Member` has many `ConsentLog` entries) with a foreign key constraint linking `ConsentLog.MemberId` to `Member.Id`.
  * The fields `Action`, `IpAddress`, `Source`, and `ConsentToken` are configured with explicit string lengths and column constraints.

### Identity Security Integration
* **IdentityService**: Implements `IIdentityService`. Uses ASP.NET Core `UserManager<Account>` and `RoleManager<Role>` to manage passwords and user profiles.
* **Authentication**: Signs standard cryptographic JWT Bearer tokens containing user ID, claims, and roles. The tokens validation parameters are verified in the request middleware.
* **Refresh Tokens**: Implements a rotating refresh token flow. Client access tokens expire in short durations (e.g. 15-30 mins), and can be silently exchanged for new access tokens using a secure refresh token stored in the database.

### Resend CRM Integration
* **ResendEmailContactService**: Communicates with the external Resend API:
  * When a member registers with opt-in preferences, the service calls `GET /segments` to check for segments like `ClientName_lead_news`. If missing, it calls `POST /segments` to create them.
  * It then calls `POST /contacts` to create a lead, saving the returned `Id` to `MemberContact`.

### Background Job Processing (Hangfire)
* **BackgroundJobService**: Implements `IBackgroundJobService` using Hangfire. Decouples long-running email confirmation tasks (`SendEmailConfirmationJob`) and newsletter registrations (`CrmSyncJob`) from the HTTP request cycle.
* **Database Connection Throttling**: The MySQL connection string for Hangfire replaces `SslMode=Disabled` with `SslMode=None` and appends `Allow User Variables=true` to satisfy driver requirements. The Hangfire background server is initialized with `WorkerCount = 2` to prevent exhausting database connection pool limits.
* **Dashboard Cookie Authorization**: Access to the Hangfire Dashboard (`/hangfire`) is protected by `HangfireAdminAuthorizationFilter`. When an admin navigates to the dashboard, a JWT bearer token is read from either the `HangfireToken` cookie or the query parameter, validated, and assessed. The request is only authorized if the user has the `"Admin"` role.

## 5. Presentation Layer (`Galvao.Presentation`)

Exposes REST APIs, hooks HTTP middlewares, and handles OpenAPI setups.

### API Controllers & Actions
All controllers extend `ApiControllerBase` which provides helper utilities like `HandleResult()` (converting `Result` structures to standard HTTP responses: 200 OK, 400 Bad Request, 404 Not Found, etc.).

| Controller | Action | Route | Authorization | Description |
|---|---|---|---|---|
| **AuthController** | Register | `POST /api/auth/register` | AllowAnonymous | Creates account + member profile + syncs CRM |
| | Login | `POST /api/auth/login` | AllowAnonymous | Verifies credentials, returns JWT tokens |
| | Refresh | `POST /api/auth/refresh`| AllowAnonymous | Refreshes expired JWT token |
| **ArticlesController**| Create | `POST /api/articles` | Admin | Creates a new article draft |
| | Update | `PUT /api/articles/{id}`| Admin | Updates article content |
| | Publish | `PUT /api/articles/{id}/publish` | Admin | Publishes/unpublishes an article |
| | GetById | `GET /api/articles/{id}`| AllowAnonymous | Reads a specific article |
| | GetPaged | `GET /api/articles` | AllowAnonymous | Paged query list of articles |
| **MembersController** | UpdateProfile | `PUT /api/members/profile` | Authorized User | Updates display name, first/last names |
| | UpdatePreferences | `PUT /api/members/preferences` | Authorized User | Updates marketing options and syncs CRM |
| | ChangeEmail | `PUT /api/members/email` | Authorized User | Changes user email and recreates Resend contact |
| | ChangePassword| `PUT /api/members/password`| Authorized User | Alters account password credentials |
| | PurgeAccount | `DELETE /api/members/purge`| Authorized User | Permanently deletes account and records audit |
| **RolesController** | Create | `POST /api/roles` | Admin | Creates a new application role |
| | Assign | `POST /api/roles/assign` | Admin | Allocates a role to a user account |
| | Remove | `POST /api/roles/remove` | Admin | Revokes a role assignment from an account |
| | GetUserRoles | `GET /api/roles/user/{userId}`| Admin | Queries role assignments for a user |
| | GetAvailableRoles| `GET /api/roles` | Admin | Lists all configured roles in the system |
| **HangfireRedirectController**| RedirectToHangfire | `GET /api/admin/hangfire-redirect` | Admin | Authorizes admin JWT and writes cookie |
| **ShowroomItemsController**| Create | `POST /api/showroomitems` | Admin | Adds a catalog showroom item |
| | AddPhoto | `POST /api/showroomitems/{id}/photos` | Admin | Appends a photo to showroom item |
| | RemovePhoto | `DELETE /api/showroomitems/{id}/photos/{photoId}` | Admin | Deletes photo from showroom item |
| | GetById | `GET /api/showroomitems/{id}` | AllowAnonymous | Reads a showroom item details |
| | GetPaged | `GET /api/showroomitems` | AllowAnonymous | Paged query list of showroom items |

### Global Exception Middleware
`CustomExceptionHandlingMiddleware` intercepts unhandled exceptions at the root of the HTTP pipeline. It formats errors into the standard JSON schema for **Problem Details (RFC 7807)**:
```json
{
  "type": "https://tools.ietf.org/html/rfc7231#section-6.6.1",
  "title": "An unexpected error occurred.",
  "status": 500,
  "detail": "Exception message details (only in Development environment)",
  "instance": "/api/showroomitems"
}
```
